# K-JIT 구현계획

작성일 2026-10-08, 전면 개정 2026-10-08. [프로토타입-기획.md](./프로토타입-기획.md)의 전체 시스템을 구현하는 순서, 작업 단위, 완료 기준, 검증, 일정, 위험을 정한다. 구현을 이어받는 사람이 처음부터 끝까지 따라갈 수 있도록 쓴다.

## 1. 인수인계 요약

### 1.1 확정된 것

- 주제는 K-JIT이다. 대표 Track은 해운 AX를 추천하되 미확정이다.
- 제출물은 실제로 동작하는 전체 시스템이다. 실시간 수집·상태·예측·결정·항만 시뮬레이터·CII·LLM 에이전트를 모두 구현한다. 사전 계산 결과만 보여 주는 정적 화면은 폴백(저장본)으로만 쓴다.
- 프런트엔드는 정적 배포(GitHub Pages + 단일 HTML)이고 백엔드는 작은 서버 한 대다. 서버가 없어도 웹 앱은 10/28 저장본으로 동작한다.
- 저장소는 10/26에 공개로 전환하고 Pages를 켠다. 10/28 제출 시 `v1.0-submission` 태그 후 `main`을 동결한다. 서버는 11/13 발표까지 켜 둔다.
- 구현 규모는 제약으로 두지 않는다. 기획서의 사업 범위는 차년도 실행 기준을 유지한다.
- 설계 토큰은 기획 6절, API·데이터 계약은 기획 7절을 따른다.

### 1.2 이미 있는 것

| 항목 | 위치 | 상태 |
|---|---|---|
| 분석 코드 | `kjit/` | A·B·C 완료. `queue_backtest.simulate()`는 `(F, M, qmat)`를 돌려준다 |
| 결과 요약 | `data/processed/*.csv`, `*.json` | git에 있음 |
| 중간 데이터·모델 | `data/processed/*.parquet`, `data/processed/models/rtd_quantile.joblib` | git에 없음. 이 컴퓨터에는 있음. 다른 컴퓨터에서는 2절 재현 명령으로 다시 만든다 |
| 원본 XML | `data/raw/vssl/` (약 450MB), `data/raw/snap/`, `data/raw/ulsan_pos/` | git에 없음 |
| 인증키 | `.env`의 `DATA_GO_KR_KEY` | git에 없음. 세 API 모두 같은 키 |
| 수집기 | `kjit/snapshot.py`(2시간), `kjit/ulsan_positions.py`(5분) | 백그라운드 실행 중. PID는 `data/snapshot.pid`, `data/ulsan_positions.pid`. WP2가 대체하기 전까지 끄지 않는다 |
| 웹 뼈대 | `web/` | Vite 8 + React 19 + TypeScript 6 템플릿. `d3-scale`, `d3-shape`, `d3-array`, `d3-interpolate`, `vite-plugin-singlefile` 설치. `App.tsx`는 템플릿 예제라 교체한다 |
| 문서 | `docs/` | 개요, 조사, 제안, 실측 A, 실측 BC, 기획, 이 문서 |

### 1.3 지켜야 할 것

- 숫자의 원천은 Python 엔진이다. 웹은 엔진이 돌려준 값을 보여 주고, 사용자 입력 계산기(CII, 정산)만 웹에서 계산한다.
- 화면의 수치는 `docs/실측-*.md`와 같아야 한다. 다르면 틀린 쪽을 고치고 문서를 갱신한다.
- 시각은 KST 고정 표시. 브라우저 시간대에 영향받지 않는다.
- `data/raw`, `data/live`, parquet, 모델, `.env`, 로그, `web/node_modules`, `web/dist*`는 커밋하지 않는다.
- 비밀값은 서버 환경 변수에만 둔다. 에이전트 호출에는 일일 비용 상한을 둔다. 비용이 드는 외부 호출은 팀 결정 뒤에 켠다.
- 팀원이 읽는 문서와 화면 문구에 개인 호칭을 쓰지 않는다.
- 제출 태그 이후 `main`에 올리지 않는다.

## 2. 재현 명령

```bash
# Python (uv)
uv sync
uv run python -m kjit.fetch_calls --start 2025-10 --end 2026-09   # 원본 수집, 약 30분
uv run python -m kjit.parse_calls
uv run python -m kjit.measure_wait
uv run python -m kjit.savings
uv run python -m kjit.berth_dataset
uv run python -m kjit.forecast                                       # 모델 저장
uv run python -m kjit.queue_backtest                                 # 백테스트 표

# 서비스 (WP2 이후)
uv run python -m kjit.service.backfill                               # 원본 → 운영 DB
uv run python -m kjit.service.app                                    # API 서버 + 스케줄러 (기본 :8000)
uv run python -m kjit.service.snapshot --out web/src/data/snapshot.json   # 웹 내장 저장본

# Web
cd web && npm install
npm run dev            # 로컬 미리보기 (VITE_API_BASE=http://localhost:8000)
npm run build          # dist/ (Pages)
npm run build:single   # dist-single/index.html (단일 파일)
```

공공데이터포털 활용신청이 필요한 API: 해양수산부_선박운항정보, 해양수산부_항만시설사용정보, 울산항만공사_항내 선박위치정보. 모두 개발계정 자동승인이다.

## 3. 아키텍처

```
해수부 입출항 신고 API ─┐                      ┌─ 상태 빌더 ─┐
울산 선박위치 API ───────┼→ 수집기(APScheduler) → SQLite(data/live/kjit.db) ─┤            ├→ 엔진(예측·결정·시뮬) → FastAPI ──→ 웹 앱(React)
data/raw 1년 백필 ──────┘                      └─ 점유 구간 ─┘                 │                 │
                                                                          Anthropic API ← 에이전트            └→ 저장본 JSON → 웹 내장 폴백
```

### 3.1 백엔드

- Python 3.11+, FastAPI, uvicorn, APScheduler, SQLite(`sqlite3` 또는 SQLAlchemy Core), pandas·numpy·scikit-learn(기존), `anthropic` SDK.
- 패키지 구조:

```
kjit/
  engine/
    features.py      berth_dataset.features_at 를 상태 표 기반으로 일반화
    model.py         모델 로드, predict_quantiles, 버전 정보
    queue.py         대기열 구성(세 정보 조건), 몬테카를로, PIT 재보정(보정 구간 PIT를 파일로 저장)
    policy.py        위험 수준별 권고, 연료·CO2(fuel.py 재사용), 남은 대기·추가 유휴
    simulate.py      항만 전체 시뮬레이터(참여율, 1차 상호작용)
    cii.py           CII 계산과 상수 로드
  service/
    db.py            스키마, 연결, 마이그레이션
    ingest.py        입출항 신고·위치 수집 작업 (snapshot.py, ulsan_positions.py 통합)
    backfill.py      data/raw → DB
    state.py         현재·과거 시점의 선석 점유, 정박지 대기, 입항 예정
    agent.py         Anthropic 호출, 도구 정의, 비용 상한, 폴백
    snapshot.py      저장본 묶음 생성
    app.py           FastAPI 앱, 라우터, 스케줄러 기동, CORS, 속도 제한
  tests/
```

- 재보정: 보정 구간(2026-06~07) PIT를 조건별로 계산해 `data/processed/models/recalibration.json`에 저장하고, 실시간과 재생이 같은 파일을 쓴다.
- 상태 빌더: `occupancy`는 단일 접안 선석 판정(`measure_wait.multi_occupancy`)을 1년 이력으로 한 번 만들고, 실시간 갱신분은 같은 규칙으로 덧붙인다. 정박지 대기 선박의 목적 선석은 사전 신고(최초 신고의 계선시설이 선석인 경우), 사용자 입력, 미상 순으로 채운다.
- 에이전트: 도구는 `get_port_state`, `predict_berth_free`, `decide`, `settlement`이며, 모델은 수치를 도구 결과에서만 가져오도록 시스템 프롬프트로 제한한다. 모델 선택과 SDK 사용법은 `claude-api` 스킬 참조를 먼저 읽고 정한다. 일일 비용 상한(기본 USD 5)과 IP당 분당 호출 제한을 둔다. 키가 없거나 상한을 넘으면 `generatedBy: "fallback"`으로 저장된 예시·템플릿을 돌려준다.

### 3.2 프런트엔드

- Vite + React 19 + TypeScript, D3 모듈(척도·경로·보간), 일반 CSS와 사용자 지정 속성. 라우터 라이브러리 없이 해시 동기화.
- 데이터 계층 `src/api.ts`: `VITE_API_BASE`로 서버를 호출하고, 실패(타임아웃 4초, 네트워크 오류, 5xx)하면 내장 `snapshot.json`으로 전환하며 상태 표식을 "저장본"으로 바꾼다. 실시간 결정·시뮬레이터 사용자 입력·에이전트는 서버가 있을 때만 활성화되고, 없으면 그 이유를 화면에 적는다.
- 단일 파일 빌드는 `SINGLE=1`로 `vite-plugin-singlefile`을 켠다. 저장본은 정적 import로 번들에 들어간다.
- 폴더 구조:

```
web/src/
  main.tsx, App.tsx, state.ts, api.ts
  data/snapshot.json
  lib/ time.ts, format.ts, motion.ts
  screens/ Ports.tsx, Decision.tsx, Simulate.tsx, Evidence.tsx, Cii.tsx, Agent.tsx
  components/ CaseHeader, ConditionToggle, RiskToggle, QueuePanel, BerthFanChart,
              RecommendationCard, RevealPanel, BerthBoard, PortMap, DataTable, Tooltip, StatusBadge
  styles/ tokens.css, base.css, screens.css
```

### 3.3 배포

- 백엔드: Docker 이미지(uv 기반), Fly.io 공유 CPU 1GB 메모리 + 1GB 볼륨(`/data`에 SQLite·모델) 또는 소형 VPS. HTTPS 자동. 환경 변수 `DATA_GO_KR_KEY`, `ANTHROPIC_API_KEY`, `AGENT_DAILY_USD_CAP`, `CORS_ORIGINS`.
- 프런트엔드: GitHub Actions가 `web/`를 빌드해 Pages에 배포. `VITE_API_BASE`는 빌드 시 주입.
- 모니터링: `GET /api/health`를 외부 가동 감시(예: 무료 uptime 서비스)로 5분마다 확인하고 실패 시 알림.

## 4. 작업 단위

각 작업 단위는 독립적으로 완료 기준을 만족해야 하고, 끝날 때마다 커밋한다. 괄호 안은 예상 소요이다. WP0~WP4가 핵심 경로이며 10/17까지 끝내 기획서 캡처를 만든다.

### WP0. 환경 (1일)

- 웹: `vite.config.ts`(`base './'`, `SINGLE=1`이면 singlefile, 출력 `dist-single`), `build:single` 스크립트, 글꼴 링크, 토큰·베이스 CSS, 템플릿 예제 제거, `api.ts` 뼈대(서버/저장본 전환).
- 백엔드: `kjit/service/app.py`에 FastAPI와 `/api/health`, `uv add fastapi uvicorn apscheduler anthropic`, Dockerfile.
- 확인: `npm run build:single` 결과를 더블클릭으로 열었을 때 React가 렌더되고 콘솔 오류가 없다. 실패하면 단일 파일 전략(일반 스크립트 출력 또는 JSON 스크립트 태그)을 먼저 고친다.

### WP1. 엔진 라이브러리화 (1.5일)

- `queue_backtest.py`, `berth_dataset.py`, `jit_backtest.py`의 로직을 `kjit/engine/`으로 옮기고 백테스트 스크립트가 엔진을 호출하게 바꾼다. 결과가 기존 `queue_backtest.csv`와 소수 첫째 자리까지 같아야 한다.
- 재보정 파일 생성. 재생 사례 1,253건 생성(세 조건의 분위수 19개·대기열·정책, 실제 결과, `featured`).
- 테스트: 정책별 합계 대조, 사례 수 1,253·선석 점유 897, 분위수 단조성.

### WP2. 수집·운영 DB·상태 빌더 (2일)

- 스키마, 백필(`data/raw/vssl` 1년 + 스냅샷), 수집 작업(30분·5분), 기존 수집기 대체.
- 상태 빌더: 지금과 과거 시점의 선석 점유·정박지 대기·입항 예정. 울산은 위치·속도로 정박지·선석 판정 보강(정박지·선석 구역 다각형을 좌표 군집에서 만든다).
- 최초 신고(사전 신고)의 실제 비율과 선행 시간을 측정해 입항 예정 목록의 근거로 문서화한다.
- 테스트: 백필 뒤 상태 빌더가 만든 과거 점유가 `berth_occupancy.parquet`와 일치. 수집 작업이 실패해도 다음 회차가 돈다.

### WP3. API 서버 (1.5일)

- 기획 7.1절의 경로 전부. 속도 제한, CORS, 오류 형식, 저장본 생성(`service/snapshot.py`).
- 테스트: 각 경로의 스키마 검사, 실시간 결정이 재생 사례와 같은 입력에서 같은 결과를 내는지 비교.

### WP4. 항차 결정 화면 (3일)

기획 5.2절. 순서: 데이터 로딩·모드 전환·사례 선택 → 머리말 → 토글 → 대기열 → 분포 띠(정적) → 권고 카드 → 결과 패널 → 보간 모션 → 호버·툴팁 → 표 보기 → 직접 입력 폼 → 휴대폰·키보드.

### WP5. 항만 현황 화면 (1.5일)

기획 5.1절. 선석 보드, 정박지 대기, 입항 예정, 울산 지도(SVG, 구역 다각형 + 점), 날짜 선택.

### WP6. 항만 시뮬레이터 (2일)

- 엔진 `simulate.py`: 기간 내 사례마다 결정, 참여율 추출(시드 고정), 1차 상호작용(참여 선박의 도착 변경이 같은 선석 다음 배의 대기열 시작에 반영), 집계.
- 격자 사전 계산(항만 4 × 조건 3 × 위험 4 × 참여율 3)과 저장본 포함. API와 화면.
- 테스트: 참여율 100%·2026-08~09·조건·위험 조합이 백테스트 문서 값과 일치.

### WP7. 근거 화면 (1일)

기획 5.4절. `GET /api/evidence`와 저장본에서만 읽는다. 10/25 울산 검증 결과 자리를 미리 둔다.

### WP8. CII 시뮬레이터 (1일)

기획 5.5절. 상수는 IMO 결의 본문에서 옮기고 출처를 적는다. 기억에 의존해 쓰지 않는다.

### WP9. 계약·정산·에이전트 (2일)

- `service/agent.py`: 도구, 프롬프트, 비용 상한, 로그, 폴백. 합성 계약 예시 세 개와 폴백 응답 작성.
- 화면: 조항 추출, 메일 구조화(결정 화면의 대기 순번 조건으로 전달), 정산 계산기, 지시문·요청서, 질의응답.
- 테스트: 키 있음·없음 두 경우 모두 화면이 유지된다. 도구 결과 밖의 수치가 답변에 들어가지 않는지 샘플 검사.

### WP10. 배포 (1.5일)

- Docker 이미지, 서버 배포, 볼륨에 DB·모델 배치, 환경 변수, HTTPS, CORS, 가동 감시.
- Pages 워크플로(공개 전환 후 활성화), `VITE_API_BASE` 주입, 단일 HTML 산출.
- 리허설: 서버를 끄고 URL·단일 HTML이 저장본으로 전환되는지 확인.

### WP11. 마무리 (1.5일)

모션·접근성·표 보기 점검, 여섯 화면 캡처, 3분 영상, zip 구성, 기획 10절 체크리스트 전부, `v1.0-submission` 태그.

### 병행 작업

- 울산 위치 데이터로 A 검증(10/25 중간 결과) → 근거 화면·기획서.
- 기획서(A4 10매). 화면 캡처가 나온 뒤 2.3절을 쓴다.
- 주최 측 문의 발송.

## 6. 검증 방법

- 엔진: pytest로 백테스트 합계 대조, 분위수 단조성, 재생·실시간 동일 입력 동일 출력.
- 수집·상태: 백필 결과와 기존 parquet 대조, 수집 실패 복구 테스트.
- API: 스키마 테스트, 속도 제한 테스트, 저장본 생성 크기 확인.
- 화면: 작업 단위마다 로컬 미리보기 캡처 검토, 기획 10절 체크리스트.
- 수치 대조: 재생 대표 사례 세 건을 `queue_backtest_cases.parquet`와, 근거 표를 실측 문서와, 시뮬레이터 격자를 백테스트 표와 대조.
- 코드: `npm run build`, `npm run lint`, `uv run pytest` 통과.

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| 심사 중 서버 다운 | 웹 앱이 저장본으로 자동 전환. 가동 감시 알림. 기획서에 저장본 폴백을 명시 |
| 단일 HTML이 `file://`에서 실행되지 않음 | WP0에서 먼저 확인. 실패 시 일반 스크립트 출력 또는 JSON 스크립트 태그 |
| 공공데이터 트래픽 한도(개발계정 10,000/일) | 30분 주기 × 4개 항만 × 쪽수로 하루 약 4,000회. 넘으면 주기를 60분으로. 운영계정 전환은 활용사례 등록이 필요해 범위 밖 |
| 사전 신고(최초 신고)가 드물어 입항 예정 목록이 비어 있음 | WP2에서 비율을 측정. 드물면 직접 입력 폼을 기본 입구로 두고 근거 화면에 적는다 |
| 에이전트 비용·남용 | 일일 비용 상한, IP 속도 제한, 입력 길이 제한, 폴백 |
| 재보정·결과 재생성 시 숫자 변동 | 시드 고정, 재생성 후 문서 대조 |
| 저장본이 커서 단일 HTML이 무거움 | 분위수 축소, 사례를 선석 점유 897건 우선, 시뮬레이터 격자 축소 |
| 브라우저 시간대 | `Asia/Seoul` 고정 포맷터 |
| 공개 전환 후 Pages 지연 | 10/26 전환으로 이틀 여유. 임시 공개 저장소 리허설 |

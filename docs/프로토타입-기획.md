# K-JIT 제출 시스템 기획

작성일 2026-10-08, 전면 개정 2026-10-08. 공모전은 제출물을 "프로토타입"이라 부르지만, 제출하는 것은 실제로 동작하는 전체 시스템이다. 공개 데이터를 계속 수집해 항만 상태를 만들고, 학습한 모델로 선석이 비는 시각을 예측하고, 위험 고려 결정으로 도착 시각과 속도를 권고하고, 항만 전체 시뮬레이션과 LLM 에이전트까지 살아 있는 서비스로 제공한다. 심사 환경의 제약(로그인 없음, URL 접속 보장, 마감 후 수정 불가)은 정적 저장본 폴백과 동결 정책으로 따로 해결한다.

구현 순서와 작업 단위는 [구현계획.md](./구현계획.md)에 둔다. 주제 배경과 근거 수치는 [K-JIT-개요.md](./K-JIT-개요.md)를 따른다.

## 1. 목적과 평가 연계

공고의 프로토타입 가점 기준은 "제출한 프로토타입이 제안 아이디어와 일관되게 연계되고, 핵심 기능과 사용자 흐름을 구체적으로 구현하며 실현 가능성을 뒷받침하는가"(최대 10점)이다. 가점을 주지 않는 조건은 "파일 손상, URL 접속 불가, 로그인·설치·권한 승인 필요"이며, 마감 후에는 파일과 URL 내용을 수정할 수 없다.

시스템이 증명해야 하는 것은 네 가지이다.

1. **지금 돌아간다.** 공개 API에서 오늘의 입출항 신고와 울산항 선박 위치를 받아 현재 선석 점유·정박지 대기를 보여 주고, 지금 들어오는 배에 권고를 낸다.
2. **핵심 흐름이 끝까지 이어진다.** 결정 시각에 선석이 비는 시각을 확률로 예측하고, 위험 수준에 맞는 도착 시각과 속도를 권고하고, 절감량과 정산 영향을 보여 주고, 재생 모드에서는 그 항차의 실제 결과를 공개한다.
3. **숫자가 실제 데이터에서 나온다.** 모든 재생 사례는 2026-08~09 해양수산부 입출항 신고이고, 실시간 화면은 공개 API의 현재 값이다. 화면에 어느 쪽인지 적는다.
4. **제안서와 같은 그림을 쓴다.** 기획서 2.3절의 그림은 이 시스템의 화면 캡처다. 그래서 시스템을 기획서보다 먼저 완성한다.

제출 형태는 세 가지를 모두 준비한다.

| 형태 | 내용 | 비고 |
|---|---|---|
| 공개 URL | 실시간 서버에 연결된 웹 앱. 서버가 응답하면 실시간, 아니면 10/28 저장본으로 자동 전환 | GitHub Pages(정적) + 백엔드 서버 |
| 단일 HTML 파일 | 10/28 저장본을 내장한 같은 웹 앱. 더블클릭으로 열린다 | 제출 zip에 포함 |
| 화면 녹화 영상 (3분 이내) | 실시간 화면과 재생 화면을 모두 담는다 | mp4, 제출 zip에 포함 |

## 2. 사용자와 핵심 흐름

주 사용자는 중소 탱커·가스·벌크 선사의 운항 담당자이다. 보조 사용자는 용선자(화주), 선박대리점, 항만공사 선석 담당이다. 심사위원은 운항 담당자의 자리에서 화면을 본다.

핵심 흐름은 다섯 단계이다.

1. 운항 담당자가 항만 현황에서 자기 배(입항 예정 또는 정박지 대기 중)를 고르거나, 항차 정보(선종, 톤수, 도착 예정, 목적 선석)를 직접 넣는다.
2. 시스템이 목적 선석의 점유 선박과 대기 순번을 보여 주고, 선석이 비는 시각의 분포를 그린다.
3. 담당자가 정보 조건(공개 데이터만 / 대기 순번 공유 / 선석계획 공유)과 위험 수준(0.1 / 0.2 / 0.3 / 0.5)을 고른다. 대기 순번은 대리점 메일을 붙여 넣으면 에이전트가 구조화해 채운다.
4. 시스템이 권고 도착 시각(RTA), 권고 속도, 절감 연료·CO2, 체선료 정산 영향, 선장 지시문·용선자 요청서 초안을 낸다.
5. 재생 모드에서는 "실제 결과 보기"로 실제 선석 가용 시각과 현행 대비 남은 대기·추가 선석 유휴를 확인한다. 실시간 모드에서는 결과가 뒤에 들어오면 기록에 남는다.

## 3. 시스템 구성

```
공개 API ──→ 수집기(30분·5분) ──→ 운영 DB(SQLite) ──→ 상태 빌더 ──→ 예측·결정 엔진 ──→ API 서버 ──→ 웹 앱
 (해수부 입출항 신고,                 (1년 이력 백필 +        (선석 점유,            (분위수 모델,         (FastAPI)       (React, 정적 배포)
  울산 선박위치)                        실시간 갱신)            정박지 대기,           대기열 몬테카를로,                      │
                                                              입항 예정)             재보정, 정책,                           ▼
                                                                                    연료·CO2)                      10/28 저장본 폴백
                                     LLM 에이전트(Anthropic API, 비용 상한) ──→ 계약 조항·대기 순번 메일 구조화·설명·질의응답
```

| 구성 | 역할 | 상태 |
|---|---|---|
| 수집 | 해수부 선박운항정보를 4개 항만(대산·울산·광양·여천)에 대해 30분마다, 울산항만공사 선박위치를 5분마다 받아 운영 DB에 쌓는다. 신고의 최초·변경·최종본을 모두 보존해 사전 신고(입항 예정)를 활용한다 | 수집기 2개 실행 중, DB·백필 신규 |
| 상태 빌더 | 단일 접안 선석의 현재 점유 선박과 경과 시간, 정박지 대기 선박과 목적 선석(사전 신고 또는 사용자 입력), 입항 예정 선박을 만든다. 울산은 위치·속도로 정박지·선석 판정을 보강한다 | 신규 |
| 예측 엔진 | B 모델(잔여 체류 분위수 GBM + CQR)과 대기열 몬테카를로, PIT 재보정 | 백테스트 코드 있음, 라이브러리화 필요 |
| 결정 엔진 | 위험 수준별 권고 도착·속도, 연료·CO2, 남은 대기·추가 유휴 | 있음, 라이브러리화 필요 |
| 항만 시뮬레이터 | 항만·기간·정보 조건·위험 수준·참여율을 넣으면 이력 전체에 JIT 정책을 적용해 대기·연료·선석 이용률 변화를 계산한다 | 신규 |
| CII 계산 | IMO G2·G4 상수로 연도별 등급 계산 | 신규 |
| LLM 에이전트 | 용선계약 조항 추출(근거 구간), 대리점 메일→대기 순번 구조화, 권고 설명, 질의응답(엔진 도구 호출), 지시문·요청서 생성. 키가 없거나 실패하면 저장된 예시로 폴백 | 신규 |
| API 서버 | 위 기능을 HTTP로 제공. 공개 읽기 전용, 쓰기 요청은 속도 제한 | 신규 |
| 웹 앱 | 화면 6개. API가 응답하면 실시간, 아니면 내장 저장본 | 뼈대만 있음 |

## 4. 화면 구성

| 화면 | 역할 | 평가 항목 | 우선순위 |
|---|---|---|---|
| 항만 현황 | 지금(또는 고른 날짜)의 선석 점유, 정박지 대기, 입항 예정. 항차 결정의 입구 | 사용자 흐름, 실현 가능성 | 1 |
| 항차 결정 | 핵심 흐름 전체. 실시간 모드와 재생 모드 | 핵심 기능, 실현 가능성 | 1 |
| 항만 시뮬레이터 | 항만 전체에 JIT를 적용한 결과 | 효과성, 혁신성 | 2 |
| 근거 | A·B·C 실측과 울산 위치 검증 결과, 한계 | 효과성, 실현 가능성 | 2 |
| CII 시뮬레이터 | 선박 제원과 연간 운항값으로 2027~2030 등급 변화 | 적합성, 효과성 | 3 |
| 계약·정산·에이전트 | 조항 추출, 메일 구조화, 정산 계산, 지시문 생성, 질의응답 | 실현 가능성, AX 적합성 | 2 |

상단 내비게이션에 여섯 화면을 두고, 현재 화면과 선택 대상은 URL 해시에 반영한다(`#ports/울산`, `#decision/live/<id>`, `#decision/replay/<id>`, `#simulate`, `#evidence`, `#cii`, `#agent`). 오른쪽 위에 데이터 상태 표식을 고정한다: "실시간 · 마지막 갱신 10:35", "재생 · 2026-08~09 실데이터", "저장본 · 10/28 기준(서버 연결 없음)".

## 5. 화면별 명세

### 5.1 항만 현황

목적: 항만의 현재 상태를 한눈에 보이고, 배를 골라 항차 결정으로 넘긴다.

- 항만 탭: 대산, 울산, 광양, 여천. 날짜 선택: 기본 "지금", 목록으로 2025-10부터 오늘까지의 날짜.
- 선석 보드: 단일 접안 선석별 가로 막대(점유 시작부터 지금까지), 선박명, 경과 시간, 남은 체류 예측 중앙값과 10~90% 구간. 과거 날짜를 고르면 그날의 점유 이력이 보인다.
- 정박지 대기: 선박명, 정박지 도착 시각, 목적 선석(사전 신고·사용자 입력·미상), 대기 중 경과. 미상이면 "목적 선석 입력" 버튼.
- 입항 예정: 사전 신고된 선박, 신고 도착 예정 시각, 목적 선석. 항차 결정으로 바로 간다.
- 울산은 지도 패널에 선박 위치(정박지·선석 구역 다각형 위에 점)를 그린다. 위치 데이터가 있는 항만만 지도를 둔다.
- 요약 띠: 접안 n척, 정박지 대기 m척, 입항 예정 k척, 마지막 갱신 시각.

완료 기준: 네 항만의 현재 상태가 뜨고, 날짜를 바꾸면 과거 상태가 뜨며, 목록에서 항차 결정으로 이동한다. 서버가 없으면 저장본으로 같은 화면이 뜬다.

### 5.2 항차 결정

목적: 한 항차의 결정을 처음부터 끝까지 보여 준다. 기획서 2.3절의 대표 그림이다.

모드:

- **실시간**: 항만 현황에서 고른 배, 또는 직접 입력(선종 그룹, 총톤수, 도착 예정, 목적 선석, 내항·외항). 결정 시각은 지금이다. 서버의 예측·결정 API를 호출한다.
- **재생**: 2026-08~09의 1,253항차. 결정 시각은 원래 도착 24시간 전(내항은 항해시간 이내). 결과는 저장된 백테스트 값이며 "실제 결과 보기"가 있다.

구성 요소:

- **항차 머리말.** 선박명(호출부호), 선종, 총톤수, 내항·외항, 항만, 목적 선석, 정박지, 도착 예정(A0), 결정 시각(τ), 권고 범위(H시간).
- **정보 조건 토글.** 조건을 바꾸면 대기열과 분포가 함께 바뀐다. 실시간 모드에서 대기 순번 조건은 대리점 메일을 붙여 넣어 에이전트가 구조화한 순번, 또는 손으로 넣은 순번을 쓴다. 선석계획 조건은 사용자가 선석계획(앞 순번 배와 도착 예정)을 넣는 폼으로 받는다.
- **위험 수준 토글.** 0.1 / 0.2 / 0.3 / 0.5. 설명 한 줄.
- **선석 대기열 패널.** 접안 중(●), 대기(○), 계획(◌). 각 선박의 체류 예측 중앙값과 구간. 선석이 비어 있으면 "결정 시각에 선석이 비어 있음"과 권고 "원래 일정 유지".
- **분포 띠.** x축은 결정 시각부터의 시간(KST 눈금). 5~95% 띠, 20~80% 띠, 50% 선. 표식은 도착 예정, 권고 도착(위험 수준에 따라 이동), 최대 지연 한계, 실제 가용 시각(재생·공개 후). 호버 십자선으로 "이 시각까지 선석이 빌 확률 N%". 표 보기 토글.
- **권고 카드.** 권고 도착·지연·속도, 절감 연료·CO2, 체선료 메모(BIMCO JIT 조항 2021), 위험 수준 네 가지 비교 표(접이식), "지시문·요청서 생성"(에이전트, 실패 시 템플릿), "왜 이 권고인가"(에이전트가 분포·대기열·정책을 근거로 설명).
- **결과 패널.** 재생: 실제 가용 시각 표식 쓸림, 현행 대기, 권고 후 남은 대기, 추가 유휴, 대기열 선박의 실제 출항. 실시간: 갱신 시각과 "다시 계산" 버튼. 결정 기록을 브라우저에 남겨 뒤에 실제 결과가 들어오면 비교할 수 있게 한다.

완료 기준: 재생 대표 사례가 첫 화면에 뜨고 토글·공개가 동작한다. 실시간 모드에서 현재 울산 입항 예정 또는 직접 입력으로 권고가 나온다. 키보드만으로 조작되고 휴대폰 폭에서 세로로 읽힌다.

### 5.3 항만 시뮬레이터

목적: 항만 전체에 JIT를 적용하면 무엇이 달라지는지 계산해 보인다. 기획서 2.6절 효과 근거의 핵심이다.

- 입력: 항만, 기간(월 단위, 2025-10~2026-09), 정보 조건, 위험 수준, 참여율(JIT를 따르는 선박 비율, 0~100%), 권고 범위(시간).
- 계산: 기간의 정박지→선석 화물선 항차마다 결정 시각에 엔진을 돌려 권고 도착을 정하고, 참여 선박의 도착을 바꾼 뒤 결과를 집계한다. 미리 계산한 격자(항만 × 조건 × 위험 수준 × 참여율 25·50·100%)는 즉시 보여 주고, 다른 입력은 서버에서 계산한다(수 초).
- 출력: 정박지 대기 합계 전후, 연료·CO2 절감, 추가 선석 유휴, 선석 이용률 전후(단일 접안 선석), 항차별 지연 분포, 선석별 표, 완전 정보 상한 대비 비율.
- 표기: 시뮬레이션은 이력 재생이며 선박 간 상호작용(한 배가 늦게 오면 다음 배가 당겨지는 효과)은 1차 근사임을 적는다.

완료 기준: 격자 결과가 즉시 뜨고, 사용자 입력으로 다시 계산되며, 결과가 백테스트 문서의 같은 조건 값과 일치한다.

### 5.4 근거

실측 문서의 수치를 화면에서 그대로 확인한다. 정박지 대기 요약 표와 분포 막대, 선석 가용 예측 지표 표, 정보 조건 × 위험 수준 절감 막대와 추가 유휴 표, 울산 위치 데이터로 한 대기 추정 검증 결과(10/25 이후 추가), 데이터와 방법, 한계 목록. 숫자는 [실측-A](./실측-A-정박지대기-2026-10-08.md), [실측-BC](./실측-BC-선석예측-JIT백테스트-2026-10-08.md)와 같아야 한다.

### 5.5 CII 시뮬레이터

- 입력: 선종(벌크선, 탱커, 가스운반선, 컨테이너선), 용량, 연간 항해거리, 연간 연료와 연료 종류, 연간 정박지 대기 시간과 대기 중 일일 연료. 항차 결정 화면의 배를 불러오면 선종·톤수가 채워진다.
- 계산: attained CII = 연간 CO2 / (용량 × 거리). 필요 CII = 기준선 × (1 − Z). 기준선 계수와 등급 경계는 IMO G2(MEPC.353(78))·G4(MEPC.354(78))에서 옮겨 출처와 함께 둔다. Z는 2023 5%, 2024 7%, 2025 9%, 2026 11%, 2027 13.625%, 2028 16.250%, 2029 18.875%, 2030 21.500%(MEPC.400(83)).
- 출력: 연도별 필요 CII와 경계, 대기 제거 전후 attained CII와 등급. 단순 가정을 적는다.

### 5.6 계약·정산·에이전트

- **조항 추출**: 용선계약 본문을 붙여 넣으면 에이전트가 JIT 도착, 신속 항해 의무, 가상 도착, 체선료 조항을 찾아 근거 구간을 강조하고 해석 메모를 붙인다. 예시 계약 세 개(합성)가 기본으로 들어 있다. 표기 "LLM 생성, 사람 검토 필요".
- **메일 구조화**: 대리점의 대기 순번 메일을 붙여 넣으면 선박·순번·목적 선석·도착 예정을 표로 만들고, 항차 결정의 대기 순번 조건에 넣을 수 있다.
- **정산 계산기**: 체선료율, 감액 비율, 연료 단가, 지연 시간, 절감 연료를 넣으면 선주·용선자별 변화와 합계를 낸다. 기본 요율은 "예시".
- **지시문·요청서**: 권고 내용으로 선장 지시문(한·영)과 용선자 감속 요청서를 생성한다. 에이전트 실패 시 템플릿.
- **질의응답**: "내일 SK2부두 01에 들어가는데 언제 도착하면 돼?" 같은 질문에 엔진 도구(상태 조회, 예측, 결정)를 호출해 답한다. 수치는 도구 결과만 쓰고 모델이 지어내지 않도록 한다.

완료 기준: 키가 있을 때 다섯 기능이 실제 LLM으로 동작하고, 키가 없거나 호출이 실패하면 저장된 예시와 템플릿으로 같은 화면이 유지된다.

## 6. 디자인 시스템

주제의 시각 어휘는 해도와 선석 계획판이다. 시간을 가로축으로 두는 판 위에 확률의 띠가 흐르고, 해도에서 항로표지를 표시하는 자홍색이 권고 도착 시각 하나에만 쓰인다. 기억에 남을 요소는 분포 띠와 권고 표식이고, 나머지는 조용하게 둔다.

### 6.2 글자

서체는 IBM Plex Sans KR(Google Fonts) 한 가족이다. 네트워크가 없으면 시스템 한글 서체로 대체되며 레이아웃이 깨지지 않아야 한다. 본문 15px/1.6, 보조 13px, 선박명 22px, 권고 도착 시각 28px 세미볼드. 시각·표 열은 `tabular-nums`, 큰 숫자는 비례 숫자. 라벨은 문장체이며 전부 대문자 라벨과 가운뎃점 연결 문자열을 쓰지 않는다.

### 6.3 레이아웃

최대 폭 1,280px, 좌측 정렬. 항차 결정은 세 열(대기열 280px / 띠 가변 / 권고 300px), 1,100px 아래에서는 띠 → 권고 → 대기열 순으로 세로. 휴대폰은 16px 가터, 가로 스크롤 없음. 패널은 그림자 카드가 아니라 면색과 1px 선으로 나눈다. 모서리 반경은 패널 6px, 버튼 4px. 번호는 실제 순서가 있는 곳(대기 순번, 흐름 단계)에만 쓴다.

### 6.4 모션

사용자가 조작했을 때만 움직인다. 조건·위험 수준을 바꾸면 띠와 표식이 240ms 보간된다. "실제 결과 보기"는 결정 시각에서 실제 가용 시각까지 수직선이 600ms 쓸려 가는 한 번의 연출이다. 실시간 갱신은 값이 바뀐 요소만 짧게 강조한다. 진입 애니메이션과 카드 호버 효과는 넣지 않는다. `prefers-reduced-motion`이면 즉시 바뀐다.

### 6.5 글쓰기와 접근성

운항 담당자의 말로 쓴다(선석, 정박지, 항차, 권고 도착, 노트, 체선료). 버튼은 일어나는 일을 적는다. 빈 화면과 오류는 이유와 다음 행동을 적는다("실시간 서버에 연결할 수 없어 10/28 기준 저장본을 보여줍니다"). 포커스 링이 보이고 키보드로 조작되며, 두 계열 이상 차트에는 범례가 있고 차트마다 표 보기가 있다. 색만으로 뜻을 전하지 않는다.

## 7. 데이터·API 계약

시각은 모두 `+09:00` ISO 8601 문자열이고 화면은 `Asia/Seoul`로 고정 표시한다. 시간 길이는 시(h) 소수 첫째 자리, 연료·CO2는 톤 소수 첫째 자리.

## 8. 정직성·표기 규칙

- 모든 화면에 데이터 상태 표식(실시간·재생·저장본)을 고정 표시한다.
- 재생 결과와 가정값(연료 계수, 요율, CII 기본값)을 구분하고, 가정값에는 "예시" 또는 "가정"을 붙인다.
- LLM이 만든 문장에는 "LLM 생성, 사람 검토 필요", 폴백에는 "저장된 예시" 또는 "템플릿"을 붙인다.
- 한계는 근거 화면에 그대로 적는다(하한 추정, 적중률 미달, 목적 선석 기지 가정, 선석계획 조건의 도착 기지 가정, 시뮬레이터의 1차 근사).
- 화면의 수치는 문서의 수치와 같아야 한다.

## 9. 배포·동결·제출

1. 백엔드는 지속 실행이 되는 작은 서버 한 대(예: Fly.io 공유 CPU + 볼륨, 또는 소형 VPS)에 컨테이너로 올린다. 스케줄러와 SQLite가 같은 프로세스 안에 있다. HTTPS, CORS는 Pages 도메인과 `file://`(null origin)을 허용한다.
2. 프런트엔드는 GitHub Pages(저장소 공개 전환 후)에 올리고, 같은 빌드에서 단일 HTML을 만든다. 둘 다 서버 주소를 설정값으로 갖고, 서버 응답이 없으면 내장 저장본으로 전환한다.
3. 비밀값(공공데이터 키, Anthropic 키)은 서버 환경 변수에만 둔다. 에이전트에는 일일 비용 상한을 둔다.
4. 10/26 저장소 공개 전환과 Pages 활성화, 서버 배포 확인. 10/27 영상·zip·전체 검수. 10/28 제출, `v1.0-submission` 태그, `main` 동결. 서버는 심사 기간(11/13 발표까지) 켜 두고 가동 상태를 매일 확인한다.
5. 마감 후 수정 금지 규칙과 실시간 데이터의 관계는 기획서에 적는다: 코드와 재생·근거·저장본은 10/28에 고정되며, 실시간 화면은 공개 API의 현재 값을 반영한다.

## 10. 검수 체크리스트

- 크롬, 엣지, 사파리, 모바일 사파리에서 여섯 화면이 열린다.
- 서버를 끈 상태에서 URL과 단일 HTML이 저장본으로 전환되어 같은 화면이 뜬다.
- 단일 HTML을 `file://`로 열었을 때 콘솔 오류가 없다.
- 실시간 항만 현황의 갱신 시각이 30분 이내다. 울산 위치가 5분 이내다.
- 실시간 항차 결정에서 직접 입력으로 권고가 10초 이내에 나온다.
- 항만 시뮬레이터 격자 값이 백테스트 문서의 같은 조건 값과 같다.
- 에이전트 다섯 기능이 키 있을 때 동작하고, 키를 지웠을 때 폴백이 동작한다.
- 재생 대표 사례 세 건의 수치가 `queue_backtest_cases.parquet`와 같다.
- 근거 화면 표가 실측 문서와 같다.
- 키보드만으로 조작되고 포커스가 보이며 `prefers-reduced-motion`이 동작한다.
- 저장본 크기, 단일 HTML 크기, 서버 메모리 사용량을 기록한다.
